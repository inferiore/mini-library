# 007 — RAG (Retrieval-Augmented Generation) Foundation

Status: approved
Area: backend
Depends on: 001-project-foundation, 003-book-management

## Objective

Build the retrieval layer that spec 008 (AI recommendations) and spec 009 (admin
embedding management) both depend on: a `rag_documents`/`book_rag_document` schema
storing one embeddable text document per book, an async embedding pipeline (Job +
queue, never synchronous), and a vector similarity search function — all built on
PostgreSQL + pgvector with Google Gemini as the embedding provider (via its
OpenAI-compatible endpoint, through the `EmbeddingServiceInterface` abstraction from
spec 001). This spec does not build the recommendation UI or LLM-generated
explanations — that's 008.

## User Story

As the system, I need a searchable, up-to-date vector representation of every book, so
that spec 008 can retrieve the most relevant books for a natural-language query and
ground its recommendations in real catalog data instead of hallucinating.

## Functional Requirements

1. Every book has exactly one associated `rag_documents` row today (via the
   `book_rag_document` pivot — a many-to-many table, not a 1:1 FK, so multiple
   documents per book can be added later — e.g. reviews or excerpts — without a schema
   change).
2. A `rag_documents.content` is a composed text template from the book's structured
   fields: title, author, category, publisher, description (there is no manuscript
   text to paragraph-chunk, so "chunking" here means "one semantically coherent
   document per book," not text-splitting).
3. Creating a book, or updating any embedding-relevant field (title, author,
   description, category, publisher), (re)writes the `rag_documents.content`, resets
   `status = pending`, and dispatches `GenerateBookEmbedding` onto the database queue
   (per spec 003's `BookObserver` hook).
4. `GenerateBookEmbedding` resolves `EmbeddingServiceInterface`, calls `embed()` with
   the document's content, stores the resulting vector plus `embedding_provider`/
   `embedding_model`, and sets `status = completed`. On any failure (HTTP error,
   timeout, malformed response) it sets `status = failed` with a stored
   `error_message`, increments `attempts`, and lets Laravel's own job retry/backoff
   handle transient failures before landing on `failed`.
5. Embedding generation is always asynchronous — never triggered synchronously inside
   the book create/update request/response cycle.
6. `App\Services\VectorSearchService::search(array $queryEmbedding, int $limit =
5): Collection<RagDocument>` returns the `limit` nearest `rag_documents` by cosine
   distance, eager-loading each result's `book`, filtered to `status = completed`
   (never surfacing a stale/failed/in-flight document as a search result).

## Non-Functional Requirements

- `rag_documents.embedding` is `vector(1536)` on Postgres (Gemini's
  `gemini-embedding-001` output width, per the user's confirmed `VECTOR_DIM=1536`),
  created via raw SQL in the migration (Laravel's schema builder has no native pgvector
  column type) — guarded to `pgsql` only; on SQLite the column is a plain nullable
  `text` (JSON-encoded array), enough to exercise the job/status state machine locally
  without real similarity search.
- Cosine distance similarity metric, **HNSW** index (`vector_cosine_ops`) — chosen over
  IVFFlat because HNSW needs no training/list-count tuning as the catalog grows, which
  matters for a library catalog that starts small and accumulates books over time.
  `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`, guarded to `pgsql`.
- The embedding provider/model/dimension are configuration (`config/ai.php`,
  env-driven), but the **column width itself is a frozen migration artifact** — it
  can't be read from `.env` at migration time (two developers with different `.env`
  values must not produce different schemas). If the provider or model ever changes to
  a different output width, that requires a new migration (see the dimension-change
  runbook below) — this is a deliberate, documented tradeoff, not an oversight.
- No automated test ever calls Gemini's real API — `Tests\TestCase` rebinds
  `EmbeddingServiceInterface` to `FakeEmbeddingService` (deterministic vector derived
  from the input string's hash, so repeated calls with the same content are stable and
  comparable in similarity-search tests).

## User Flow

Not directly user-facing — this is the retrieval substrate. The only observable
behavior in this spec (beyond internal state) is: create/edit a book → its embedding
status transitions `pending → processing → completed` (or `failed`) automatically and
asynchronously, visible via spec 009's admin UI once that spec lands.

## Database Changes

- `rag_documents`: `id` (bigint PK), `content` (text), `embedding` (`vector(1536)` on
  Postgres / `text` on SQLite), `status` (string: `pending|processing|completed|failed`,
  default `pending`), `embedding_provider` (string, nullable), `embedding_model`
  (string, nullable), `error_message` (text, nullable), `attempts` (unsigned int,
  default 0), `processed_at` (timestamp, nullable), timestamps.
- `book_rag_document`: `id` (bigint PK), `book_id` (FK → `books.id`, cascade delete),
  `rag_document_id` (FK → `rag_documents.id`, cascade delete), unique
  (`book_id`,`rag_document_id`), timestamps.
- HNSW index on `rag_documents.embedding`, Postgres-only (guarded migration).
- **Dimension-change runbook** (documented here, not implemented until actually
  needed): if the embedding provider/model ever changes to a different output width, a
  new migration drops and recreates the `embedding` column and its HNSW index at the
  new width, resets every row to `status = pending`, and a backfill command
  re-dispatches `GenerateBookEmbedding` for all books. This is acceptable because
  `content` is fully derived from `books` columns — nothing user-authored is at risk of
  loss.

## API/Application Changes

- `app/Models/RagDocument.php`: `status` enum cast, `belongsToMany(Book::class)`
  through the pivot, `scopeCompleted()`.
- `App\Jobs\GenerateBookEmbedding` (constructed with a `$ragDocumentId`, not a model
  instance, to avoid stale-serialization issues): resolves
  `EmbeddingServiceInterface` via DI in `handle()`; `$tries = 3`,
  `backoff()` with increasing delay for transient failures.
- `App\Services\RagDocumentService::syncForBook(Book $book): void` — builds/updates the
  templated content, upserts the `rag_documents` row + pivot, resets status, dispatches
  the job. Called from `BookObserver` (spec 003).
- `App\Services\VectorSearchService::search()` — issues the raw pgvector `<=>` cosine
  distance query on Postgres; on SQLite, either a stubbed/unsupported path (since
  SQLite can't do real vector search) — flagged below for confirmation.
- `config/ai.php` additions: `embedding.dimensions` (1536, informational/validation
  use, not schema-controlling).

## Edge Cases

- A book with a null/empty `description` still gets a valid (shorter) composed
  document — not an error, not a skipped embedding.
- A transient embedding API failure (timeout, 5xx) retries per the job's backoff policy
  before landing on `failed` with a captured error message.
- A permanent failure (e.g. invalid API key, 401) should still exhaust retries and land
  on `failed` cleanly rather than retrying indefinitely.
- Deleting a book cascades to delete its `book_rag_document` pivot rows and, if no
  other book references it, the orphaned `rag_documents` row (only relevant once a
  document can belong to multiple books — today's 1:1 cardinality makes this
  straightforward cascade-on-delete).
- Re-editing a book back to the same field values it already had should not
  unnecessarily re-embed (the observer diff-check from spec 003 prevents this).

## Acceptance Criteria

- Creating a book results in a `rag_documents` row transitioning `pending →
processing → completed` asynchronously (never synchronously in the request cycle).
- Editing an embedding-relevant field re-triggers the pipeline; editing a
  non-embedding-relevant field (e.g. `total_copies` via spec 004) does not.
- A simulated embedding provider failure results in `status = failed` with a captured
  `error_message`, without crashing the request that triggered it (since it's always
  async).
- `VectorSearchService::search()` returns results ordered by similarity and excludes
  non-`completed` documents.
- No automated test makes a real network call to Gemini.

**Flag for approval**: SQLite has no vector similarity operator, so
`VectorSearchService::search()` has no real equivalent to test locally. Recommend: the
fast local SQLite suite tests the job/status state machine only (dispatch, success,
failure, retry), and the actual similarity-ranking behavior is tested exclusively via
`phpunit.ci.xml` against real Postgres+pgvector. Confirm this split is acceptable
before implementation, since it means `VectorSearchService`'s core behavior is
untested in the fast default local loop.

## Test Cases

1. Feature test: creating a book dispatches `GenerateBookEmbedding` and results in
   `status = completed` when the fake embedding service succeeds.
2. Feature test: editing `description` re-dispatches the job; editing `total_copies`
   alone does not.
3. Unit test: `GenerateBookEmbedding` sets `status = failed` with an `error_message`
   when the embedding service throws, after exhausting retries.
4. Unit test: `RagDocumentService::syncForBook()` composes the expected `content`
   template from a book's fields, including the empty-description case.
5. Postgres-only test (`phpunit.ci.xml`): `VectorSearchService::search()` returns
   results ordered by actual cosine similarity against known fixture embeddings, and
   excludes a `failed`/`pending` document from results.
6. Feature test: no test in the suite ever hits a real network call (enforced via the
   fake being the bound implementation in `Tests\TestCase`).
