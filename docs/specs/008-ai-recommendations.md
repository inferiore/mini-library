# 008 — AI Recommendations

Status: implemented
Area: backend+frontend
Depends on: 001-project-foundation, 003-book-management, 007-rag

## Objective

Let any authenticated user describe what they want to read in natural language and get
book recommendations grounded entirely in the library's actual catalog (via spec 007's
retrieval layer), each with an explanation of why it matches, generated by an LLM
(Gemini, via `LLMServiceInterface`) that is given only the retrieved context — never
free to invent books that don't exist in `rag_documents`.

## User Story

As a member, I want to describe the kind of book I'm looking for in my own words and
get relevant, explained recommendations from the actual library catalog, so that I can
discover books I wouldn't have found by browsing or exact-match search alone.

## Functional Requirements

1. An authenticated user submits a free-text query (e.g. "something about software
   architecture that's practical, not too academic, useful for senior developers").
2. The system embeds the query (via `EmbeddingServiceInterface`), retrieves the top-K
   (default 5) most similar `completed` `rag_documents` via
   `VectorSearchService::search()` from spec 007.
3. The retrieved documents' content (and their books' availability) are passed to the
   LLM as the _only_ source of book information in the prompt — the prompt explicitly
   instructs the model to recommend only from the provided context and never invent a
   title/author not present in it.
4. The response returned to the user, per recommended book: title, author, a short
   explanation of why it matches the query (LLM-generated, grounded in the retrieved
   content), and current availability (`available_copies`/`total_copies`, and whether
   it's currently checkout-able).
5. If retrieval returns zero relevant documents (e.g. an empty/unembedded catalog, or a
   query with no reasonable match), the system returns a clear "no matching books
   found" response rather than asking the LLM to invent something anyway.
6. The recommendation UI is visually and structurally distinct from spec 006's search
   results — clearly labeled "AI Recommendations" vs. "Search Results," so a user never
   confuses a semantic AI suggestion with an exact catalog match.
7. Unavailable recommended books are clearly marked unavailable in the response, not
   hidden — a "hallucination-free" recommendation can still legitimately point at a
   book that's fully checked out.

## Non-Functional Requirements

- The recommendation endpoint is rate-limited per user (e.g. Laravel's built-in
  throttle middleware, a conservative default like 10 requests/minute) — this is an
  LLM-backed endpoint with real per-call cost, unlike the rest of the app's routes.
- No automated test calls a real LLM — `Tests\TestCase` rebinds `LLMServiceInterface`
  to `FakeLLMService` (deterministic templated output), so recommendation tests assert
  against known fixture behavior, not live model output.
- The LLM call must not block indefinitely — a request timeout on the HTTP client
  (`OpenAiCompatibleLLMService`) with a clear user-facing error if the provider is
  slow/unreachable, distinct from the "no matches found" case.

## User Flow

1. User visits the dashboard's "What would you like to read?" widget → types a
   description → submits.
2. System embeds the query, retrieves relevant catalog documents, asks the LLM to
   explain the match for each, and returns results.
3. User sees a list of recommended books (title, author, why-it-matches, availability)
   — can click through to a book's detail page for the full record and to check it out
   if available.
4. If nothing relevant is found, the user sees a plain "no matching books" message, not
   a generic error or an empty screen.

## Database Changes

None beyond spec 007's `rag_documents`/`book_rag_document`. This spec is read-only
against that data (no new tables).

## API/Application Changes

- `App\Http\Requests\RecommendationRequest` — validates the free-text `query`.
- `App\Services\RecommendationService::recommend(string $query, int $limit =
5): array` — orchestrates: embed query → `VectorSearchService::search()` → build a
  grounded prompt from the retrieved documents → `LLMServiceInterface::generate()` →
  parse the model's structured response (should request the LLM to return
  strictly-formatted output, e.g. JSON, so parsing doesn't rely on fragile text
  scraping) → attach live availability from each result's `Book` (queried fresh, not
  trusted from the LLM's output, since availability changes independently of the
  catalog description).
- `RecommendationController@store` — thin, rate-limited via `throttle` middleware,
  delegates to `RecommendationService`, returns the recommendation list as an Inertia
  response (or a JSON endpoint consumed by the dashboard widget via a client-side
  fetch, since this is a single-purpose interactive widget rather than a full page
  navigation — pick whichever fits this app's existing Inertia conventions more
  naturally once 002-006 establish them).
- The LLM prompt template lives in a dedicated class/view
  (`App\AI\Prompts\RecommendationPrompt`) rather than inlined in the Service, so the
  grounding instructions ("only recommend from the books listed below; never invent a
  title") are easy to review/audit in one place.

## UI Changes

- Dashboard "AI Recommendations" widget: text input + submit, loading state during the
  LLM round-trip, results rendered distinctly from search results (e.g. a labeled
  card style with a "Why this matches" section per book), "no matches" empty state.

## Authorization

- Any authenticated user (`MEMBER`, `LIBRARIAN`, `ADMIN`) can request recommendations —
  per the master requirements' MEMBER permission list, but nothing about this feature
  is role-sensitive, so no reason to restrict it further.

## Validation Rules

- `query`: required, string, min 3 / max 500 characters (long enough to be meaningful,
  short enough to bound embedding/LLM cost per request).

## Edge Cases

- A nonsensical or empty-after-trim query is rejected by validation before any
  embedding/LLM call is made (don't spend an API call on invalid input).
- A query that retrieves documents but the LLM's response fails to parse as the
  expected structured format is handled as a clear "something went wrong, try again"
  error, not a raw parse exception leaking to the user (never expose internal errors,
  per the master doc's security section).
- A recommended book that gets deleted/soft-deleted between retrieval and response
  rendering (rare race) is filtered out rather than shown as a broken link.
- Rate limit exceeded returns a clear "too many requests, try again shortly" response,
  not a generic 429 with no context.

## Acceptance Criteria

- A query relevant to the seeded catalog returns books that are actually present in
  `rag_documents`/`books` — never a fabricated title/author.
- Each recommendation includes an explanation grounded in the retrieved content, not a
  generic templated blurb unrelated to the query.
- Availability shown per recommendation reflects the book's live `available_copies`,
  not a stale value baked into the LLM's response.
- An empty/no-match scenario returns a clear empty state, not an LLM-invented result.
- The endpoint is rate-limited and returns a clear error when exceeded.
- No automated test calls a real LLM or embedding API.

## Test Cases

1. Feature test: a query matching fixture books (via the fake embedding service's
   deterministic similarity) returns those books with fake-LLM-generated explanations.
2. Feature test: recommended books' availability in the response matches the current
   `books` table state, not any cached/stale value.
3. Feature test: a query with no relevant `completed` documents (e.g. empty catalog)
   returns a "no matches" response, not a fabricated one.
4. Feature test: an unauthenticated request is rejected (auth required).
5. Feature test: exceeding the rate limit returns the throttled response with a clear
   message.
6. Feature test: a malformed/unparseable fake-LLM response is handled gracefully (clear
   error, no leaked exception detail, no 500).
7. Feature test: validation rejects an empty/too-short/too-long query before any
   service call is attempted (assert the fakes were never invoked).
